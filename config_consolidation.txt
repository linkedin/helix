  Here's the consolidated picture:

  ---
  2. Redundant/Overlapping Configs

  Several configs exist at multiple scopes with unclear precedence:

  Config: P2P_MESSAGE_ENABLED
  Scopes: Cluster + Resource
  Resolution: Resource > Cluster > false
  Problem: Acceptable but undocumented
  ────────────────────────────────────────
  Config: DELAY_REBALANCE_ENABLED
  Scopes: Cluster + Resource + Instance
  Resolution: Resource > Cluster; Instance can override
  Problem: 3-scope override is confusing
  ────────────────────────────────────────
  Config: DELAY_REBALANCE_TIME
  Scopes: Cluster + Resource
  Resolution: Resource > Cluster
  Problem: OK, but defaults differ
  ────────────────────────────────────────
  Config: MAX_PARTITIONS_PER_INSTANCE
  Scopes: Cluster + Resource
  Resolution: Both checked independently
  Problem: Cluster-level (GLOBAL_*) is dead code
  ────────────────────────────────────────
  Config: MAX_CONCURRENT_TASK
  Scopes: Cluster + Instance
  Resolution: Instance > Cluster (default 40)
  Problem: Undocumented fallback
  ────────────────────────────────────────
  Config: REBALANCE_PREFERENCE + GLOBAL_REBALANCE_PREFERENCE
  Scopes: Both on ClusterConfig
  Resolution: Different code paths
  Problem: Confusing naming
  ────────────────────────────────────────
  Config: IdealState vs ResourceConfig
  Scopes: Most resource props exist in both
  Resolution: Merge logic in Resource.java
  Problem: Historical debt

  Recommendation:
  - Establish a documented resolution hierarchy: Resource > Instance > Cluster >
   Default
  - Merge IdealState and ResourceConfig into a single config surface (IdealState
   is the ZK-persisted form; ResourceConfig should be the API form)
  - Remove GLOBAL_MAX_PARTITIONS_ALLOWED_PER_INSTANCE since per-resource
  MAX_PARTITIONS_PER_INSTANCE is what's actually enforced

  ---
  3. Configs with High Blast Radius (Need Guardrails)

  These configs have outsized impact on cluster behavior:

  Config: MAX_OFFLINE_INSTANCES_ALLOWED
  Impact: If exceeded, entire pipeline switches to maintenance mode
  Risk: Cluster-wide outage if misconfigured
  ────────────────────────────────────────
  Config: NUM_OFFLINE_INSTANCES_FOR_AUTO_EXIT
  Impact: Controls auto-exit from maintenance
  Risk: Can cause premature exit
  ────────────────────────────────────────
  Config: ERROR_OR_RECOVERY_PARTITION_THRESHOLD_FOR_LOAD_BALANCE
  Impact: Blocks ALL load-balance transitions if error count exceeds threshold
  Risk: Silent rebalance freeze
  ────────────────────────────────────────
  Config: STATE_TRANSITION_THROTTLE_CONFIGS
  Impact: Complex JSON blob controlling all transition rates
  Risk: Hard to configure correctly
  ────────────────────────────────────────
  Config: INSTANCE_CAPACITY_KEYS + DEFAULT_INSTANCE_CAPACITY_MAP
  Impact: WAGED rebalancer fails validation if these are inconsistent
  Risk: Cluster rebalance failure
  ────────────────────────────────────────
  Config: REBALANCE_PREFERENCE
  Impact: Changes WAGED objective weights
  Risk: Can cause uneven distribution
  ────────────────────────────────────────
  Config: PERSIST_BEST_POSSIBLE_ASSIGNMENT / PERSIST_INTERMEDIATE_ASSIGNMENT
  Impact: Changes what gets written to ZK
  Risk: Affects all spectators/consumers

  Recommendation: Add server-side validation for these configs in the REST API
  layer (ClusterAccessor.java) before accepting writes.

  ---
  4. Standardization Opportunities

  a) Throttle Config Simplification

  Current state: Customers must construct a complex
  StateTransitionThrottleConfig JSON with RebalanceType × ThrottleScope × 
  MaxPartitions combinations. There are 4 rebalance types × 4 throttle scopes =
  16 possible combinations.

  Proposal: Provide named profiles:
  - CONSERVATIVE — low transition rates, safe for production
  - MODERATE — balanced (current typical settings)
  - AGGRESSIVE — high throughput for initial setup/migration
  - CUSTOM — current behavior for advanced users

  b) WAGED Capacity Model

  Current state: Requires coordinating 3 configs (INSTANCE_CAPACITY_KEYS,
  DEFAULT_INSTANCE_CAPACITY_MAP, per-resource PARTITION_CAPACITY_MAP) across
  cluster and resource scopes. Validation happens late (during rebalance).

  Proposal: Single capacity_model config object validated at write time.

  c) Delayed Rebalance

  Current state: 3-scope override (cluster, resource, instance) with ENABLED
  boolean + TIME duration at each scope.

  Proposal: Simplify to cluster-level default + resource-level override only.
  Instance-level override is rarely used and creates debugging complexity.

  ---
  5. Helix-ACM Gap

  The ACM service acts as a translation layer for 7 cluster types (Ambry,
  Espresso, Venice, Pinot, Seas, CHO, Tectonic) but:
  - Does not standardize or validate the underlying Helix config knobs
  - Each cluster type has its own plugin with bespoke config patterns
  - No enforcement that cluster types use configs consistently

  Recommendation: ACM should define per-cluster-type config profiles — a
  validated set of configs known to work for each system. This prevents
  individual teams from accidentally setting conflicting or dead configs.

  ---
  6. Proposed Config Tiers

  To guide customers, organize configs into tiers:

  Tier: Essential
  Description: Must be set for cluster to function
  Example Configs: TOPOLOGY, STATE_MODEL, NUM_PARTITIONS, REPLICAS
  Who Sets: Customer at creation
  ────────────────────────────────────────
  Tier: Tuning
  Description: Affects performance/safety, has sane defaults
  Example Configs: DELAY_REBALANCE_TIME, throttle configs,
    MAX_PARTITIONS_PER_INSTANCE
  Who Sets: Customer with guidance
  ────────────────────────────────────────
  Tier: Advanced
  Description: WAGED capacity model, P2P messaging, maintenance thresholds
  Example Configs: INSTANCE_CAPACITY_KEYS, REBALANCE_PREFERENCE, PERSIST_*
  Who Sets: Expert / Helix team
  ────────────────────────────────────────
  Tier: Internal
  Description: Should not be customer-facing
  Example Configs: Dead configs, VIEW_CLUSTER_*, ABNORMAL_STATES_RESOLVER_MAP
  Who Sets: Remove or hide

  ---
  Summary of Action Items

  1. Remove 10-12 dead configs — zero risk, reduces confusion
  2. Document config resolution hierarchy — Resource > Instance > Cluster >
  Default
  3. Add write-time validation for high-blast-radius configs in REST API
  4. Merge IdealState/ResourceConfig surface for cleaner API
  5. Create throttle profiles (CONSERVATIVE/MODERATE/AGGRESSIVE/CUSTOM)
  6. Simplify delayed rebalance to 2-scope (cluster + resource)
  7. ACM config profiles per cluster type
  8. Tier classification in documentation

  Would you like me to proceed with any of these — for example, creating a
  design doc following the docs/design/ template, or starting implementation on
  the dead config removal?

❯ but conceptually both are controlling parallelism on the cluster be it

⏺ You're raising a legitimate design question. Both are fundamentally about "how
   much concurrent work can this instance handle." Let me lay out why they're
  separate today and whether that separation is justified.

  Why They're Separate Today

  It's historical. The task framework was bolted on as a separate subsystem
  after the core rebalance pipeline was already mature. They have different:

  - Pipeline code paths — GenericHelixController runs the resource pipeline and
  the task pipeline as separate stage sequences
  - State models — task resources use the Task state model
  (INIT→RUNNING→COMPLETED), while regular resources use
  MasterSlave/LeaderStandby
  - Lifecycle — a state transition is short (seconds to minutes), a task can run
   for hours
  - Priority semantics — state transitions distinguish RECOVERY vs LOAD_BALANCE
  (recovery should not be throttled the same way), tasks don't have this concept

  The Argument For Unifying

  From the participant's perspective, both consume the same physical resources
  (CPU, memory, disk I/O, network). A node running 40 concurrent tasks AND
  processing 20 state transitions simultaneously is doing 60 units of concurrent
   work. The current system doesn't account for this cross-interaction at all —
  the two budgets are completely independent.

  This means:
  - An instance could be at 100% task capacity AND 100% transition capacity
  simultaneously, effectively 2x overloaded
  - There's no way to express "this instance can handle 50 total units of
  concurrent work, split between tasks and transitions as needed"
  - A customer has to independently tune two separate throttles with no guidance
   on how they interact

  The Argument Against Unifying

  There are real semantic differences that make a naive merge problematic:

  1. Recovery priority. If a master goes down, RECOVERY transitions need to
  happen immediately regardless of task load. A unified budget could starve
  recovery behind tasks. Today the RebalanceType dimension handles this — you
  can set RECOVERY_BALANCE throttle separately (or not throttle it at all).
  2. Different controllers. State transitions are dispatched by the controller
  leader. Tasks are assigned by the task pipeline. Merging them requires
  cross-pipeline coordination that doesn't exist today.
  3. Duration asymmetry. A state transition holds a "slot" for seconds. A task
  holds a slot for hours. A unified counter would mean one long-running task
  blocks one transition slot for the task's entire lifetime, which is wasteful.

  My Assessment

  The user-facing complexity IS a real problem, but a full merge isn't the right
   answer. A better design would be a two-level model:

  Instance Work Budget (total capacity)
  ├── State Transition Budget (sub-budget)
  │   ├── RECOVERY: unlimited or high
  │   └── LOAD_BALANCE: configurable
  └── Task Budget (sub-budget)
      └── configurable

  Where:
  - The total budget is a single config: "max concurrent work units on this
  instance"
  - The sub-budgets are either auto-derived (e.g., 60% transitions / 40% tasks)
  or explicitly set
  - Recovery transitions could have a reserved pool that bypasses the shared
  budget
  - This gives operators one primary knob while preserving the ability to tune
  internals

  This would require wiring the StateTransitionThrottleController and
  AbstractTaskDispatcher to share a common capacity abstraction — probably a new
   class like InstanceWorkBudget that both pipelines check/charge against.

  The WAGED rebalancer already has the INSTANCE_CAPACITY_KEYS /
  INSTANCE_CAPACITY_MAP concept for partition placement. The work budget could
  be modeled as another capacity dimension (e.g., CONCURRENT_WORK) that both
  pipelines respect, making it consistent with the existing capacity model.

  What Espresso/Venice/Ambry Actually Need

  Looking at the data:
  - Espresso tunes instance-level LOAD_BALANCE throttle (1-20) and uses default
  task capacity (40). These operate independently today.
  - Venice doesn't use either Helix-level throttle — they handle it in
  application code, which itself suggests the Helix abstractions aren't meeting
  their needs.
  - Ambry uses state transition throttling but doesn't appear to use the task
  framework heavily.

  None of them coordinate between the two budgets, which means the
  cross-interaction problem exists in production but is just unmanaged.

  This is a concrete simplification opportunity — worth capturing in a design
  doc if you want to pursue it.

  9. Helix-ACM Analysis

  What ACM Does

  Translation layer between NSS deployment automation and Helix REST API.
  Manages instance lifecycle (EVACUATE, SWAP_IN, SWAP_OUT, DISABLE) for 7
  cluster types.

  ACM's Config Interaction

  From HelixClient.java:
  - Reads ClusterConfig, InstanceConfig
  - Sets InstanceOperation (EVACUATE, SWAP_IN, etc.)
  - Reads/writes DELAY_REBALANCE_TIME
  - Checks isDelayRebalaceEnabled() and delay window

  From HelixClusterSetupTool.java (test setup only):
  - INSTANCE_CAPACITY_KEYS = [PARTCOUNT]
  - DEFAULT_INSTANCE_CAPACITY_MAP = {PARTCOUNT: 100}
  - DEFAULT_PARTITION_WEIGHT_MAP = {PARTCOUNT: 1}
  - TOPOLOGY = /mz/host/applicationInstanceId
  - TOPOLOGY_AWARE_ENABLED = true
  - PERSIST_BEST_POSSIBLE_ASSIGNMENT = true
  - FAULT_ZONE_TYPE = mz
  - MAX_OFFLINE_INSTANCES_ALLOWED = 2

  ACM Per-System Plugins

  System: Espresso
  Plugin: 3 ClusterNameResolvers, 3 InstanceNameResolvers, AutoAckHook
  Config-Related: Hook is a TODO stub — no capacity set
  ────────────────────────────────────────
  System: Venice
  Plugin: 2 ClusterNameResolvers, InstanceNameResolver, VirtualTopology hooks
  (4)

  System: Ambry

  ACM Gap

  - Each cluster type has operational plugins but no config templates

  12. Key Observations

  Config Surface vs Actual Usage

  - 120+ defined, ~12 dead (34% of ClusterConfig)
  - Espresso uses ~30, Venice ~15, Ambry ~20
  - No system uses: RESOURCE_PRIORITY_FIELD,
  RELAXED_DISABLED_PARTITION_CONSTRAINT, PREFERRED_SCORING_KEYS,
  GLOBAL_MAX_PARTITIONS_ALLOWED_PER_INSTANCE

  Standardization Gaps

  - No standard config profiles across systems
  - Each system wraps Helix in its own abstraction
  - ACM is pass-through with no enforcement
  - No documentation on recommended values per system
  - No server-side validation for high-blast-radius configs

  Incident Patterns

  - Highest-severity incidents from config interactions, not individual wrong
  values
  - P2P + MissingTopState, throttle + recovery priority, capacity + weight
  validation
  - Venice doesn't use features that would help it (cancellation, error
  threshold, priority)
  - Espresso built external validation because Helix lacks server-side
  validation

  Task vs Partition Parallelism

  - MAX_CONCURRENT_TASK_PER_INSTANCE and STATE_TRANSITION_THROTTLE are separate
  systems
  - Only Espresso uses both (tasks for bulk ops + partitions for data)
  - Venice/Ambry don't overlap — configs can remain separate
  - Task framework has its own dead configs
  (GLOBAL_TARGET_TASK_THREAD_POOL_SIZE)
